LLMOps

Ship LLM features behind evals and guardrails

Goal: a prompt or model change ships only if an eval set says it got better, within a cost and latency budget.

  1. Build an eval set from real traffic

    Curate golden inputs + expected behaviour, including the edge cases that have burned you.

  2. Score it automatically in CI

    Exact-match where you can, rubric/LLM-judge where you can’t; block merges that regress.

    promptfoo eval -c evals.yaml --assert
# fail the PR if pass-rate drops below threshold

  3. Add output guardrails

    Validate the response against a schema, cap tokens, and check for refusals/hallucination markers before returning it.

  4. Set cost and latency budgets

    Cache responses, trim context, and route each task to the cheapest model that passes its eval.

  5. Log prompts, responses and traces

    You can’t debug what you don’t capture — keep the full request with a trace id.

  6. Canary a change before 100%

    Send a new prompt/model to a slice of traffic and watch quality and spend before rolling out.
