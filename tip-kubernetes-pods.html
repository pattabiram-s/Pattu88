Kubernetes

Set requests, limits, and probes on every pod

Four fields per workload that quietly prevent a large share of cluster incidents — set them once in your base manifest and inherit them everywhere.

The spec, and the failure each field prevents

resources:
  requests: { cpu: 100m, memory: 128Mi }   # scheduler places you sanely
  limits:   { cpu: 500m, memory: 256Mi }   # one pod can’t starve the node
readinessProbe:                            # no traffic until actually ready
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 5
  periodSeconds: 10
livenessProbe:                             # restart if wedged
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 15
  periodSeconds: 20
startupProbe:                              # slow starters: don’t kill while booting
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30
  periodSeconds: 5

Why each one matters

  • No requests → the scheduler guesses, packs nodes wrong, random noisy-neighbour stalls.
  • No memory limit → one leaking pod OOMs the whole node and its neighbours.
  • No readiness → deploys briefly serve 502s because traffic hits not-ready containers.
  • No startup probe → liveness kills a slow-booting app in a restart loop.

Tune with data, then enforce

Set initial numbers from kubectl top / VPA recommendations, add a PodDisruptionBudget so drains don’t take you to zero, and bake all of it into the Helm chart base so every new service inherits it — a few lines once, a whole class of 2 a.m. pages gone.
