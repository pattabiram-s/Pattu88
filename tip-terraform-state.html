Treat state like production data

Your infrastructure state file is as critical as a production database — protect it, version it, and never hand-edit it casually.

Remote, locked, versioned, encrypted

Keep Terraform state in a remote backend with state locking, object versioning, and encryption at rest. Locking is what saves you the day two engineers run apply at the same time; versioning is what saves you when an apply goes wrong.

Never edit state by hand without a net

Reach for terraform state mv, import, and rm over editing JSON directly. If you must surgery the state, back it up first and have a tested path to roll back. A corrupted state file can make Terraform try to destroy and recreate live infrastructure.

Blast radius and drift

Split state by environment and by blast radius so a mistake in one stack can’t touch another. Run plan in CI on every change and alert on drift — infrastructure that changed outside code is how ‘it works in staging’ stories begin.

What ‘good’ looks like

Every environment reproducible from code, plans reviewed before apply, and a state file you could lose and rebuild without panic because it is backed up and access-controlled.
