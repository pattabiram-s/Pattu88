Treat state like production data

Remote, locked, versioned and encrypted state — and the only way you touch it is through terraform state, after a backup.

A backend that locks and can be rewound

DynamoDB gives you locking so two applies can’t race; S3 versioning + encryption give you point-in-time recovery and at-rest protection. This block is the difference between “oops” and “outage.”

terraform {
  backend "s3" {
    bucket         = "acme-tfstate"
    key            = "prod/network/terraform.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "tf-locks"   # state locking
    encrypt        = true         # SSE at rest
    # enable Versioning on the bucket for rollback
  }
}

Split by blast radius

One state file per environment and component (prod/network, prod/data…). A mistake in one plan then can’t propose destroying another, and plans stay small and reviewable.

Do surgery with a net

Never hand-edit the JSON. Pull a backup first, then use the state subcommands with a lock timeout so a stuck lock doesn’t wedge the team.

terraform state pull > backup.tfstate         # before ANY surgery
terraform state mv aws_instance.old aws_instance.new
terraform import -lock-timeout=120s aws_s3_bucket.logs acme-logs

Catch drift automatically

Run a read-only plan on a schedule; exit code 2 means reality diverged from code — alert on it before it becomes a mystery.

terraform plan -detailed-exitcode   # 0=none, 2=drift → notify
