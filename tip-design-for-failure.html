Reliability

Design for the failure you'll actually have

Most outages are mundane — a full disk, an expired certificate, a bad deploy. Engineer for those before the exotic ones.

Alert on the boring killers first

Disk filling up, certificates about to expire, a dependency starting to throttle, error rate creeping after a deploy. These cause the majority of real incidents. Cover them with alerts that fire early, while there’s still time to act calmly.

Rehearse the rollback

A rollback you have never tested is a hope, not a control. Practise it, time it, and make it a single well-known command or button. The confidence to ship quickly comes from knowing you can undo quickly.

Automate the recovery you repeat

If you’ve run the same manual fix twice at 2 a.m., automate the third. Health checks that restart, disks that alert before they’re full, deploys that auto-roll-back on error budget burn — turn runbooks into code the system runs itself.

Then, and only then, the edge cases

Region failover and chaos testing matter, but they’re the wrong first investment if a forgotten cert can still take you down. Fix the common failures first; they’re cheaper to prevent and far more likely to happen.
