Observability

Instrument before you optimise

You can't tune what you can't see. Emit structured logs, RED/USE metrics and a trace id threaded through everything — then pivot metric → trace → log.

Log structured, with the ids that let you join

Plain-text logs are a dead end under load. Emit JSON with a trace_id so you can jump from a spiking metric to the exact request.

{"ts":"2026-10-10T09:12:04Z","level":"error","svc":"checkout",
 "trace_id":"4bf92f3577b34da6","user":"u_8831",
 "msg":"charge failed","err":"gateway timeout","latency_ms":812}

Measure the four signals that explain behaviour

  • Services → RED: Rate, Errors, Duration (p50/p95/p99).
  • Resources → USE: Utilisation, Saturation, Errors.
  • Alert on symptoms users feel (error rate, p99) — not on CPU for its own sake.
# p99 latency per route, last 5 min (PromQL)
histogram_quantile(0.99,
  sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))

Thread one id end to end

Propagate the W3C traceparent header across every hop (OpenTelemetry auto-instrumentation does most of it). With exemplars you click a point on the latency graph and land on the slow trace — the bottleneck names itself instead of you guessing.
