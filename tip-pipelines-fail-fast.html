Make pipelines fail fast, loudly

Order jobs so the cheapest, most-likely-to-fail check runs first, cap every job's runtime, and make the red build name the one thing that broke.

Gate the slow jobs behind a 30-second one

Put format, lint, type-check and unit tests in one quick job, and make build and integration needs: it so they never run when the quick job is red. Most breakage is caught in the first thirty seconds, and you stop paying for the slow stages.

jobs:
  quick:                     # ~30s, catches most breakage
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint && npm run typecheck
      - run: npm test -- --bail    # stop at first failing test

  build:
    needs: quick               # never runs if quick fails
    timeout-minutes: 15
    runs-on: ubuntu-latest
    steps: [ ... ]

Make the failure name itself

A status check that just says “pipeline failed” trains people to hit re-run. Emit annotations that point at the file and line, and write a one-line job summary so the reason shows without opening logs.

# fail with a GitHub annotation on the exact file/line
echo "::error file=src/auth.ts,line=42::token check returns undefined"
# surface the headline in the PR checks UI
echo "### ❌ 1 test failed: auth > rejects expired token" >> "$GITHUB_STEP_SUMMARY"

Protect the time budget

  • Target < 5 min PR feedback; set timeout-minutes on every job so a hung step fails instead of burning 6 hours.
  • Cache deps and Docker layers; run independent suites as a matrix in parallel.
  • pytest --maxfail=1 -q / --bail — don’t run 400 tests to tell me the first one broke.

Don’t auto-retry flakes into silence

A blanket “retry failed jobs 3×” hides real regressions. Quarantine a flaky test (skip + ticket) so the signal stays trustworthy — green has to mean shippable or people route around the gate.
