9 DevOps & SecOps lessons from running production

Pattabi Ram S Last updated: October 10, 2026 12 min read

These are the lessons I keep coming back to after years of building and securing production systems — the ones that actually prevent 2 a.m. pages. Each is short, opinionated, and comes with the exact commands or config I’d reach for. Skim the list, or jump to what you need.

What’s inside

  1. Make pipelines fail fast, loudly
  2. Least privilege is a default, not a cleanup task
  3. Treat state like production data
  4. Design for the failure you'll actually have
  5. Keep secrets out of images and repos
  6. Instrument before you optimise
  7. Right-size on real usage, not guesses
  8. Set requests, limits, and probes on every pod
  9. Shift security left, but gate at the right

1. Make pipelines fail fast, loudly

CI/CD

Order jobs so the cheapest, most-likely-to-fail check runs first, cap every job's runtime, and make the red build name the one thing that broke.

Gate the slow jobs behind a 30-second one

Put format, lint, type-check and unit tests in one quick job, and make build and integration needs: it so they never run when the quick job is red. Most breakage is caught in the first thirty seconds, and you stop paying for the slow stages.

jobs:
  quick:                     # ~30s, catches most breakage
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint && npm run typecheck
      - run: npm test -- --bail    # stop at first failing test

  build:
    needs: quick               # never runs if quick fails
    timeout-minutes: 15
    runs-on: ubuntu-latest
    steps: [ ... ]

Make the failure name itself

A status check that just says “pipeline failed” trains people to hit re-run. Emit annotations that point at the file and line, and write a one-line job summary so the reason shows without opening logs.

# fail with a GitHub annotation on the exact file/line
echo "::error file=src/auth.ts,line=42::token check returns undefined"
# surface the headline in the PR checks UI
echo "### ❌ 1 test failed: auth > rejects expired token" >> "$GITHUB_STEP_SUMMARY"

Protect the time budget

  • Target < 5 min PR feedback; set timeout-minutes on every job so a hung step fails instead of burning 6 hours.
  • Cache deps and Docker layers; run independent suites as a matrix in parallel.
  • pytest --maxfail=1 -q / --bail — don’t run 400 tests to tell me the first one broke.

Don’t auto-retry flakes into silence

A blanket “retry failed jobs 3×” hides real regressions. Quarantine a flaky test (skip + ticket) so the signal stays trustworthy — green has to mean shippable or people route around the gate.

2. Least privilege is a default, not a cleanup task

Security

Grant nothing by default, then let the cloud's own access data — not a guess — tell you the few permissions a workload truly uses.

Delete permissions from evidence, not opinion

You don’t have to guess what a role needs. AWS records what each role actually touched; generate a tight policy from real CloudTrail activity and drop the rest.

# which services has this role NOT used in 90 days? (then remove them)
aws iam generate-service-last-accessed-details --arn "$ROLE_ARN"
aws iam get-service-last-accessed-details --job-id "$JOB_ID"

# let Access Analyzer propose a least-privilege policy from CloudTrail
aws accessanalyzer start-policy-generation \
  --policy-generation-details '{"principalArn":"'$ROLE_ARN'"}'

Scope with conditions, not just actions

A tight policy constrains the resource and the context, not only the verb — so a leaked token can’t reach the whole account.

{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::acme-reports/${aws:PrincipalTag/team}/*",
  "Condition": { "StringEquals": { "aws:ResourceAccount": "111122223333" } }
}

Prefer credentials that expire

  • CI → GitHub OIDC assume-role, not a long-lived AKIA… key.
  • EKS pods → IRSA / Pod Identity, so each pod gets its own scoped role.
  • Humans → SSO + short session, with just-in-time elevation for the rare admin action.

Fail the PR on broad policy

Catch "Action": "*" and "Resource": "*" in review with checkov/tfsec so nobody ships a wildcard by reflex.

checkov -d . --check CKV_AWS_1,CKV_AWS_49   # flags wildcard IAM
tfsec .                                     # aws-iam-no-policy-wildcards

3. Treat state like production data

IaC

Remote, locked, versioned and encrypted state — and the only way you touch it is through terraform state, after a backup.

A backend that locks and can be rewound

DynamoDB gives you locking so two applies can’t race; S3 versioning + encryption give you point-in-time recovery and at-rest protection. This block is the difference between “oops” and “outage.”

terraform {
  backend "s3" {
    bucket         = "acme-tfstate"
    key            = "prod/network/terraform.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "tf-locks"   # state locking
    encrypt        = true         # SSE at rest
    # enable Versioning on the bucket for rollback
  }
}

Split by blast radius

One state file per environment and component (prod/network, prod/data…). A mistake in one plan then can’t propose destroying another, and plans stay small and reviewable.

Do surgery with a net

Never hand-edit the JSON. Pull a backup first, then use the state subcommands with a lock timeout so a stuck lock doesn’t wedge the team.

terraform state pull > backup.tfstate         # before ANY surgery
terraform state mv aws_instance.old aws_instance.new
terraform import -lock-timeout=120s aws_s3_bucket.logs acme-logs

Catch drift automatically

Run a read-only plan on a schedule; exit code 2 means reality diverged from code — alert on it before it becomes a mystery.

terraform plan -detailed-exitcode   # 0=none, 2=drift → notify

4. Design for the failure you'll actually have

Reliability

Alert the boring killers — full disks, expiring certs, bad deploys — early, and make rollback one command you have actually run.

Alert before it hurts, not after

  • Disk: warn at 80%, page at 90% — not when it’s 100% and the DB is already down.
  • Certs: check expiry daily, alert under 14 days.
  • Deploys: watch error rate / latency for 10 min after rollout and auto-revert on spike.
  • Dependencies: alert on p99 latency and throttling (429/503), not just “is it up”.
# cert expiry in days — wire into a daily check
exp=$(echo | openssl s_client -connect api.example.com:443 2>/dev/null \
  | openssl x509 -noout -enddate | cut -d= -f2)
echo "$(( ($(date -jf '%b %d %T %Y %Z' "$exp" +%s) - $(date +%s)) / 86400 )) days left"

Rollback is a control, not a hope

A rollback you’ve never run is a guess. Keep the last known-good image tag, make reverting a single command, and rehearse it so shipping fast is safe.

kubectl rollout undo deploy/web            # to previous ReplicaSet
kubectl rollout undo deploy/web --to-revision=42

Automate the fix you’ve done twice

Ran the same 2 a.m. fix twice? Make the system do it the third time: liveness probes that restart a wedged process, canary/auto-rollback on error-budget burn, log-rotation before the disk fills. Turn runbooks into code the platform runs itself.

5. Keep secrets out of images and repos

Secrets

Images and git history are forever and get scanned within minutes — inject credentials at runtime, catch leaks before merge, and rotate on a schedule.

Prove the image and history are clean

A secret in a container layer survives even after you “delete” it, and a committed key stays in git history. Scan both — in pre-commit and in CI — so a leak is caught in the PR, not by a bot crawling GitHub.

gitleaks detect --source . --redact        # repo + history
docker history --no-trunc myimg:latest     # did a secret land in a layer?
trivy image --scanners secret myimg:latest

Inject at runtime, scoped and short-lived

The app should receive a secret, never ship with one. Mount it from a secrets manager at start-up and scope it tightly; prefer tokens with a TTL over permanent keys.

# External Secrets Operator: K8s Secret synced from the real vault
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
spec:
  refreshInterval: 1h
  secretStoreRef: { name: aws-secrets, kind: ClusterSecretStore }
  target: { name: db-credentials }
  data:
    - secretKey: password
      remoteRef: { key: prod/db, property: password }

Make rotation routine

  • Automate rotation on a schedule so a key you’re afraid to rotate never exists.
  • On a leak: revoke first (kill the live key), then rotate — order matters.
  • Block the commit at the source with a pre-commit hook: gitleaks protect --staged.

6. Instrument before you optimise

Observability

You can't tune what you can't see. Emit structured logs, RED/USE metrics and a trace id threaded through everything — then pivot metric → trace → log.

Log structured, with the ids that let you join

Plain-text logs are a dead end under load. Emit JSON with a trace_id so you can jump from a spiking metric to the exact request.

{"ts":"2026-10-10T09:12:04Z","level":"error","svc":"checkout",
 "trace_id":"4bf92f3577b34da6","user":"u_8831",
 "msg":"charge failed","err":"gateway timeout","latency_ms":812}

Measure the four signals that explain behaviour

  • Services → RED: Rate, Errors, Duration (p50/p95/p99).
  • Resources → USE: Utilisation, Saturation, Errors.
  • Alert on symptoms users feel (error rate, p99) — not on CPU for its own sake.
# p99 latency per route, last 5 min (PromQL)
histogram_quantile(0.99,
  sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))

Thread one id end to end

Propagate the W3C traceparent header across every hop (OpenTelemetry auto-instrumentation does most of it). With exemplars you click a point on the latency graph and land on the slow trace — the bottleneck names itself instead of you guessing.

7. Right-size on real usage, not guesses

Cost

The steady wins — sizing from measured usage, switching off idle non-prod, tagging for ownership — beat any one big migration.

Size from what it actually uses

Over-provisioning “to be safe” is the biggest line on most bills. Read real usage and let the tooling recommend the shape.

kubectl top pods -A --sort-by=memory     # who’s actually using what
# EKS: VerticalPodAutoscaler in recommend-only mode suggests requests
# AWS: Compute Optimizer flags over-provisioned EC2/EBS/Lambda

Switch off what no one is using

Dev and staging that run 24/7 for a 9-to-6 team pay triple for idle time. Scale non-prod to zero outside hours.

# kube-downscaler: annotate a namespace to sleep nights + weekends
downscaler/uptime: "Mon-Fri 08:00-20:00 Asia/Kolkata"

Find the quiet waste

# unattached EBS volumes still billing
aws ec2 describe-volumes --filters Name=status,Values=available \
  --query 'Volumes[].{id:VolumeId,GiB:Size}'
# load balancers with zero healthy targets, old snapshots, idle EIPs …

Make the bill accountable

Tag every resource with owner, env and service, and enforce it (AWS Config / SCP). Untagged spend is unowned spend — and a 30-minute monthly review of idle resources recovers more, more reliably, than a yearly re-architecture.

8. Set requests, limits, and probes on every pod

Kubernetes

Four fields per workload that quietly prevent a large share of cluster incidents — set them once in your base manifest and inherit them everywhere.

The spec, and the failure each field prevents

resources:
  requests: { cpu: 100m, memory: 128Mi }   # scheduler places you sanely
  limits:   { cpu: 500m, memory: 256Mi }   # one pod can’t starve the node
readinessProbe:                            # no traffic until actually ready
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 5
  periodSeconds: 10
livenessProbe:                             # restart if wedged
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 15
  periodSeconds: 20
startupProbe:                              # slow starters: don’t kill while booting
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30
  periodSeconds: 5

Why each one matters

  • No requests → the scheduler guesses, packs nodes wrong, random noisy-neighbour stalls.
  • No memory limit → one leaking pod OOMs the whole node and its neighbours.
  • No readiness → deploys briefly serve 502s because traffic hits not-ready containers.
  • No startup probe → liveness kills a slow-booting app in a restart loop.

Tune with data, then enforce

Set initial numbers from kubectl top / VPA recommendations, add a PodDisruptionBudget so drains don’t take you to zero, and bake all of it into the Helm chart base so every new service inherits it — a few lines once, a whole class of 2 a.m. pages gone.

9. Shift security left, but gate at the right

DevSecOps

Catch issues in the PR where they're cheap to fix, and still enforce a hard policy at admission and runtime — both, not either.

Scan in the pull request

Find the problem where the fix is a quick edit: images, IaC and secrets, all on the PR.

trivy fs --scanners vuln,secret,misconfig .   # deps + keys + bad config
tfsec .            # or: checkov -d .            # IaC misconfig
gitleaks detect --source . --redact            # committed secrets

Enforce at admission — shifting left doesn’t replace the gate

Early feedback reduces what reaches prod; it doesn’t guarantee it. Block the risky things at the cluster door with a policy engine.

# Kyverno: refuse :latest and unsigned images
apiVersion: kyverno.io/v1
kind: ClusterPolicy
spec:
  validationFailureAction: Enforce
  rules:
    - name: disallow-latest
      match: { any: [{ resources: { kinds: [Pod] } }] }
      validate:
        message: "Pin an image tag; :latest is not allowed"
        pattern: { spec: { containers: [{ image: "!*:latest" }] } }

Verify provenance at runtime

cosign verify --key cosign.pub registry/acme/web:1.8.2   # signed by us?

Keep the gate trusted

A slow or noisy gate gets bypassed. Keep scans fast, tune out false positives, and make the required fix obvious — a gate people route through, not around.
